# 0024：使用强类型规则 JSON 驱动战斗资料

## 状态

已采纳。

## 背景

`game_skill_detail` 和 `game_ability_detail` 持续增加战斗字段，导致关系表变宽、稀疏字段默认值难以表达，管理端也需要维护与战斗规则对应的 JSON 结构。Battle Engine 同时要求规则输入可校验、可冻结、可重放，不能在运行时解释任意脚本。

## 决策

- Skill 和 Ability 的基础资料、展示文案、稳定身份、启用状态、版本和时间字段归入各自主表。
- 战斗规则存入主表的非空 `rules` JSONB 字段；不再保留独立的 `game_skill_detail` 或 `game_ability_detail` 持久化表。
- `rules` 以 Battle Engine 执行时机组织结构，但只允许组合已由 Go 实现的规则原语，不建立通用脚本 DSL。
- Protobuf 定义规则的强类型嵌套消息和 `oneof`；管理端以生成的 JSON/结构化表单维护，服务端拒绝未知字段。
- 不持久化 `schemaVersion`。规则结构变化通过停机维护一次性重写全部资料，部署代码只支持当前结构。
- PostgreSQL 仅检查 `rules` 非空且为 JSON object；完整类型、范围、互斥条件和资料引用由统一的纯 Go 规则编译器校验。
- 不依赖 JSON 内引用的数据库物理外键，但保存、导入、启动和 Battle 冻结时必须验证引用完整性。
- 保存、导入、服务启动和 Battle 创建共用同一个编译器；任何启用资料编译失败都拒绝启动或创建 Battle。
- Engine 保持纯 Go 状态机，接收编译后的强类型规则；规则数组不依赖 JSON 顺序，必要时使用显式优先级和稳定排序。

## 后果

新增已有规则原语的参数或组合不需要修改 Engine；新增全新的战斗机制仍需修改 Go、Protobuf、编译器、测试和部署资料。资料错误会在写入、导入或启动阶段暴露，而不是延迟到玩家开战。
