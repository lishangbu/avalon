# Starllow 宝可梦中文图鉴数据源评估

> 核查日期：2026-08-03。只依据站点自身页面、前端代码、静态数据、robots、公开仓库检索及其可识别上游页面；版权判断不构成法律意见。
>
> 授权状态更新：项目方已于 2026-08-03 确认取得网站授权。公开页面无法验证的授权范围以项目方持有的原始授权凭证为准；本文对公开许可证缺失的调查仍作为来源审计记录保留，不再据此阻止 Avalon 建立经授权的离线数据快照。
>
> 实施状态：经授权导入的关系数据已经固化进单一 SQL 资料基线，图片已经进入受控 RustFS 备份。运行仓库不再保留原始 JSON、下载脚本或在线同步工具，构建、部署和运行均不访问该站点。

## 结论

**在项目方持有的网站授权范围内，可以将 `pokedex.starllow.com` 作为一次性导入来源；部署权威必须是仓库维护的 SQL 基线与 RustFS 备份，而不是远程站点或仓库内原始快照。**

这个站在技术上很容易读取：它把宝可梦、招式、特性和物品整理为公开静态 JSON，数据量大、简体中文字段丰富，网页 `robots.txt` 还允许抓取。但站点没有数据来源说明、许可证、使用条款、版权页、公开仓库、版本化发布或开发者 API 契约；静态资源域的 CORS 也只放行站点自身，而不是作为第三方开放 API。

更重要的是，[皮卡丘详情 JSON](https://s.starllow.com/pokedex/pokemon/0025-%E7%9A%AE%E5%8D%A1%E4%B8%98.json)中的“原型剖析”“细节”“名字来源”等大段文字，与 [52Poké 的皮卡丘页面](https://wiki.52poke.com/zh-hans/皮卡丘)在内容和表述上高度对应；JSON 中却没有来源、作者、许可证、原文链接或署名字段。52Poké 的[版权声明](https://wiki.52poke.com/wiki/神奇宝贝百科:版权声明)规定原创文字为 CC BY-NC-SA 3.0，要求署名、非商业和相同方式共享，图片、音频及宝可梦相关权利还不在该许可范围。公开页面本身无法证明 Starllow 能向 Avalon 提供商业使用或再分发授权，因此项目方必须保留已取得的非公开授权凭证，并按凭证覆盖的内容和用途使用快照。

因此，Avalon 可以在已取得授权的范围内完成一次性下载和转换，但不能把“公开可下载”“robots 允许”或“有 JSON”本身当成授权依据。上游没有版本化发布能力；授权凭证与原始来源审计应在受控合规存储中保存，运行仓库只保留已审查的 SQL 基线和必要的决策证据。图片及长篇表达性内容是否进入产品仍以实际授权范围为准。

## 可见技术接口

站点的当前前端代码暴露了以下读取模式：

- [全国图鉴列表 JSON](https://s.starllow.com/pokedex/pokedex/national.json)：`id`、简体中文名、属性、筛选标签、世代和图标位置；
- [皮卡丘详情 JSON](https://s.starllow.com/pokedex/pokemon/0025-%E7%9A%AE%E5%8D%A1%E4%B8%98.json)：名称、简介、原型、细节、各语言名称来源、形态、种族值、克制、获得方式、图鉴文本、进化、可学习招式和图片名等；
- [招式列表 JSON](https://s.starllow.com/pokedex/move_list.json)：中日英名称、属性、分类、威力、命中、PP、说明、世代；
- [特性列表 JSON](https://s.starllow.com/pokedex/ability_list.json)：中日英名称、说明、拥有者计数和世代；
- [物品列表 JSON](https://s.starllow.com/pokedex/item_list.json)：分层分类、名称、说明和图标名；
- 详情文件还按 `pokemon/{编号}-{中文名}.json`、`moves/{中文名}.json`、`abilities/{中文名}.json` 等规则组织。

这些端点返回标准 JSON，带 `ETag` 与 `Last-Modified`，所以做一次性技术原型很方便。但没有 schema、分页、版本、许可和变更日志；文件名还直接依赖可变的中文展示名。它们只能证明“可以读取”，不能证明“适合依赖”或“允许再利用”。

## 数据来源风险证据

[Starllow 皮卡丘页](https://pokedex.starllow.com/pokemon/%E7%9A%AE%E5%8D%A1%E4%B8%98)和对应 JSON 包含以下资料组合：

- “根据官方的说法，皮卡丘最初的设计原型……”一段；
- 乐百氏“倍加超”、任天堂 Space World'99、不同地区读音等细节；
- 日文、中文各地区、英文、法文、德文等名称及词源；
- 多世代获得方式、图鉴文本、形态、进化和招式表。

这些内容也集中出现在 [52Poké 皮卡丘页](https://wiki.52poke.com/zh-hans/皮卡丘)，部分句序和表达高度一致。Starllow 没有保留 52Poké 页面上的脚注、修订链接和 CC 署名信息，其 JSON 也未声明自行原创或取得转载许可。因此：

1. 不能确认结构化数值以外的长文本由谁创作、采用什么版本、是否正确履行上游许可；
2. 不能凭 Starllow 的公开访问状态绕过 52Poké 的非商业、署名、相同方式共享条件；
3. 52Poké 自身又明确说图片、音频和 Pokémon 相关商标/知识产权不在其 CC 许可范围，Starllow 更无从转授这些权利。

## 建议

1. **部署只使用固化制品。** 关系数据来自 SQL 基线，图片字节来自同一发布批次的 RustFS 备份；构建、部署和运行不访问 Starllow。
2. **保留授权与来源审计。** 在受控合规存储中保存完整授权凭证、下载日期、原始 URL、文件大小和 SHA-256，不把原始快照放入运行仓库。
3. **按授权范围转换。** 结构化事实、长篇文案和图片分别核对授权范围，只把当前领域模型需要且已审查的结果固化进受控 SQL 基线和 RustFS 备份。
4. **更新时停机发布。** 新一批上游资料在仓库外完成下载与差异审查，以更新后的 SQL 基线和 RustFS 备份发布，不在线同步或静默重写正在运行的对象。
5. **继续交叉校验关键事实。** 中文名称、战斗数值和规则参数仍应与官方图鉴、游戏规则或另一独立来源核对，避免把上游整理错误直接固化为 Current Game Data。
